# Frontmatter parse cost: full vs. selective (athenaeum#2178)

Durable record of the benchmark issue athenaeum#2178 asks for: a before/after
timing of the full-wiki frontmatter parse, on a synthetic fixture corpus this
script generates (never the operator's live store). Harness committed at
[`scripts/measure_frontmatter_parse_cost.py`](../../scripts/measure_frontmatter_parse_cost.py).

## Result

This is a shared container; other lane processes run on the same 12 CPUs,
so wall-clock numbers on a single repeat can swing with ambient load. This
run was taken after an earlier, heavily-contended attempt (six concurrent
full-suite `pytest` runs; see below) was abandoned and the host quieted down
to at most one other active process. Repeats are INTERLEAVED (`full`,
`selective`, `full`, `selective`, ...) so any remaining load drift is spread
evenly across both candidates rather than biasing whichever one happened to
run second, and **min** (the least-contended repeat observed) is reported
as the primary statistic alongside median.

**Corpus generation (4.02s) is reported separately from parse timing below
— it is not included in any of the parse numbers.**

| Candidate | min wall time | median wall time | pages/s (at min) |
|---|---|---|---|
| `full` (`parse_frontmatter`, today's behavior) | 23.771s | 25.636s | 1,094 |
| `selective` (`parse_frontmatter_selective`, `EntityIndex`'s opted-in keys) | 15.412s | 18.168s | 1,687 |

**Speedup: 1.54x (min/min), 1.41x (median/median).**

Sanity check against the real opted-in caller end to end
(`EntityIndex(scratch_corpus)`, read + parse + index bookkeeping, one run):
**16.207s** for 26,000 pages (1,604 pages/s) — consistent with the
function-level `selective` number above.

Raw per-repeat timings (4 interleaved reps, seconds) —
`full`: [24.086, 37.466, 27.186, 23.771];
`selective`: [19.408, 19.636, 16.929, 15.412].
(Rep 2's 37.466s `full` outlier is the residual other process; min/min is
reported as primary for exactly this reason.)

### Cross-checks against this result

- **Uncontended, no-file-I/O, in-memory check** (5,000 pages held in memory,
  same corpus shape, run during development with no other process active):
  full 0.859s vs. selective 0.538s — **1.60x**. Matches this run's 1.54x
  min/min closely, which is the evidence the 1.4-1.6x range is the real
  effect and not an artifact of ambient contention.
- **A separate attempt at this same 26,000-page x 4-rep comparison, run
  while six sibling lanes were each running a full `pytest -q` suite
  concurrently on this container**, produced unusable numbers: `full` min
  27.3s / median 44.1s / rep range 27-55s; `selective` min 58.9s / median
  60.2s / rep range 59-66s (selective slower than full, which is impossible
  given every other measurement here and in-process microbenchmarking). That
  run is NOT used as the recorded result — it is cited here only to show why
  machine-context disclosure matters and why this measurement was re-taken
  on a quieter host rather than reported as-is.

## What this does and does not show

- This is a parse-cost-only measurement: file read + YAML parse, the same
  shape `EntityIndex._load` and `librarian.rebuild_index` use. It is not an
  end-to-end `athenaeum status` or compile timing.
- The speedup is specific to the key set requested (`uid`, `name`, `type`,
  `metadata`, `aliases`) and this corpus's long-tail shape (4-10 `sources`
  with a nested `provenance` block, 5-15 `claims` entries per page, sized to
  approximate the issue's own ~117-constructed-objects-per-page citation). A
  caller requesting more keys, or a corpus with a thinner long tail, would
  show a smaller ratio.
- Per-call recall latency is explicitly out of scope for athenaeum#2178 and is
  not measured here.
- Reproduce with `python scripts/measure_frontmatter_parse_cost.py --pages 26000 --repeats 4` (or any `--pages`/`--repeats`); the generator always writes under a fresh `tempfile.mkdtemp()` unless `--scratch-dir` is given, never under `~/knowledge`.
