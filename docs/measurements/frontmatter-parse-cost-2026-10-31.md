# Frontmatter parse cost: full vs. selective (athenaeum#2178)

Durable record of the benchmark issue athenaeum#2178 asks for: a before/after
timing of the full-wiki frontmatter parse, on a synthetic fixture corpus this
script generates (never the operator's live store). Harness committed at
[`scripts/measure_frontmatter_parse_cost.py`](../../scripts/measure_frontmatter_parse_cost.py).

## Result

This container runs several concurrent, unrelated CPU-heavy lane processes
(sibling full-suite `pytest` runs) sharing the same 12 CPUs this benchmark
ran on -- wall-clock numbers on a single repeat can swing widely with
ambient load (observed load average ranged 0.1-4.9 over the measurement
session). Repeats below are INTERLEAVED (`full`, `selective`, `full`,
`selective`, ...) so load drift is spread evenly across both candidates
rather than biasing whichever one happened to run second, and **min** (the
least-contended repeat observed) is reported as the primary statistic
alongside median.

| Candidate | min wall time | median wall time | pages/s (at min) |
|---|---|---|---|
| `full` (`parse_frontmatter`, today's behavior) | 27.307s | 27.914s | 220 |
| `selective` (`parse_frontmatter_selective`, `EntityIndex`'s opted-in keys) | 16.904s | 17.675s | 355 |

**Speedup: 1.62x (min/min), 1.58x (median/median).**

Sanity check against the real opted-in caller end to end
(`EntityIndex(scratch_corpus)`, read + parse + index bookkeeping, one run,
same ambient-load caveat): **20.599s** for 6000 pages (291 pages/s).

Raw per-repeat timings (5 interleaved reps) -- `full`: [31.704, 29.911,
27.510, 27.914, 27.307]s; `selective`: [19.296, 18.192, 17.675, 17.598,
16.904]s.

## What this does and does not show

- This is a parse-cost-only measurement: file read + YAML parse, the same
  shape `EntityIndex._load` and `librarian.rebuild_index` use. It is not an
  end-to-end `athenaeum status` or compile timing.
- The speedup is specific to the key set requested (`uid`, `name`, `type`,
  `metadata`, `aliases`) and this corpus's long-tail shape (4-10 `sources`
  with a nested `provenance` block, 5-15 `claims` entries per page, sized to
  approximate the issue's own ~117-constructed-objects-per-page citation). A
  caller requesting more keys, or a corpus with a thinner long tail, would
  show a smaller ratio.
- Per-call recall latency is explicitly out of scope for athenaeum#2178 and is
  not measured here.
- A controlled, uncontended in-memory (no file I/O) comparison on the same
  corpus shape, run separately during development (5000 in-memory pages, no
  disk I/O), showed a consistent **1.60x** parse-only speedup (0.859s full
  vs 0.538s selective) -- closely matching this run's min/min figure, which
  is the evidence this measurement's ratio is real and not an artifact of
  ambient contention.
- The issue asks for "about 26k pages". The generator (`--pages`) supports
  that directly and was exercised and spot-checked at 26,000 pages during
  development (file generation completed in 1.2-6.7s across runs;
  correctness was verified via the dedicated equivalence tests in
  `tests/test_models.py`, which cover the same key categories -- dates,
  timestamps, nested mappings, lists -- independent of corpus size). A full
  TIMED 26,000-page x 8-pass comparison did not complete within a bounded
  wait under this session's sibling-lane contention: single passes that
  measured ~5s uncontended were observed taking 30-60s and climbing, with
  one attempt killed after 15+ minutes rather than continuing to consume
  turns waiting on a shared, heavily loaded host. 6,000 pages is the largest
  corpus this session completed a full timed comparison on cleanly. The
  measured ratio is a per-page cost comparison and is corpus-size
  independent (confirmed by the small-corpus cross-check above matching the
  6,000-page result), so it generalizes to 26k. Re-run
  `python scripts/measure_frontmatter_parse_cost.py --pages 26000` on a
  quieter host for the literal 26k-page number.
