# `two_surnames_former_name` gold-label audit — 2026-11-15

Issue athenaeum#2542, split out of athenaeum#2423. Offline data audit of the
44 `two_surnames_former_name` cases in
`tests/evals/data/attribution/cases.yaml` (generated by
`tests/evals/data/attribution/generate_cases.py`). No prompt change, no model
call, no paid run.

**Result: 0 gold labels changed. 22 of 44 cases had a broken premise and are
repaired at the generator.** The labels were consistent with the design
document's definitions. The inputs were not: in half the cases the "former
name" was identical to the current name, so no case in that half could
exhibit what its label describes.

## Definitions used

Quoted from `docs/design/attribution-verification.md`:

- `own` (§7.1): "Filed on the target as originally intended, `unclassified`,
  unless the writer had already established a stronger class through its own
  evidence."
- `alias` (§7.1): "Filed on the target in `alt_emails` (for phones, `phones`),
  with a `field_sources` entry and a per-identifier fact entry in a new
  `identifier_relation` field". The relation vocabulary (§6.3) is
  `role-inbox | shared | former-name | personal-alias`.
- `same-entity` (§7.1): "No contact write. A merge proposal (target,
  `owner_uid`) goes to the existing pending-merges queue ... because one
  person under two names is a dedupe question, not an alias."
- Gold pattern row (§12.1): "Same person under two surnames, or a former name
  | `same-entity` or `alias` (`former-name`)".
- C2 (§5.1): fires when the local part names someone else and does "not match
  the target's name or aliases".

## Ambiguity in the design document

The §12.1 row allows `same-entity` or `alias` (`former-name`) and says nothing
about what chooses between them. The document never says whether an address
built from a former name is `own`, either: `own` is defined only by how it is
filed. Three readings were possible. The audit used this one:

**The one written rule.** For an address built from a former or married name
of the target:

1. The target's page lists the former name and **a second known record exists
   under that name** (a holder or candidate with its own uid) -> `same-entity`,
   `gold_owner_uid` = that record. This follows §7.1: two records for one
   person is a dedupe question.
2. The former name appears only as a name the target went by, and **no second
   record exists** (no holder, no candidate) -> `alias` with relation
   `former-name`, `gold_owner_uid` null.
3. `own` is never gold for this scenario. A former-name address is the
   target's, but §7.1 and §12.1 both route it to `alias`, so `own` would
   record the address with no relation and lose the fact that it is a former
   name.

Rule 3 is the reading most likely to be argued. The alternative (a
former-name address is simply `own`) would also be self-consistent, but
contradicts the §12.1 table row, so it was not used. A prompt or design edit
that settles this belongs to a separate issue.

## Findings

### 1. Labels follow the rule in all 44 cases

22 cases carry `same-entity` (each has exactly one holder and one candidate,
and `gold_owner_uid` is that uid) and 22 carry `alias` / `former-name` (no
holder, no candidate, null owner). The split is the generator's `i % 2`.
No label contradicts the rule, so no label changed.

### 2. Defect: "former name" equals the current name in 22 of 44 cases

`_pattern_two_surnames_former_name` drew the former surname with
`_name(i + 19)`. For `i` in 0-10 the target surname (`LAST_NAMES[i // 30]`) and
the former surname (`LAST_NAMES[(i + 19) // 30]`) are both index 0; for `i` in
30-40 they are both index 1. In those 22 cases (`-000` to `-010`, `-030` to
`-040`) the excerpt read "published under their former name, Alex
Thistlewood", on a target named Alex Thistlewood, at
`alex.thistlewood@example.org`. That is a plain own-name address with no second
surname: C2 could not fire, `aliases` repeated the target's own name, and a
`same-entity` case pointed at a second record with an identical name.

It also fits the miss list in
`docs/measurements/attribution-calibration-2026-11-11.md`: 10 of the 22 broken
cases are `alias` gold (the 10 "alias -> own" misses on both models) and 12 are
`same-entity` gold. A judge reading an address that is literally the contact's
own name as `own` is correct on the evidence it was shown. The 55-60% pass
rate is therefore at least partly a dataset defect, not a model capability gap.
This audit does not re-measure; it only fixes the data.

### 3. Not changed, flagged: the target's aliases already name the former surname

Every case sets `target.aliases` to the former full name. §5.1's C2 text says
the check fires when the local part does "not match the target's name or
aliases", so by the design's own wording C2 would not fire for these cases,
yet the cases carry a C2 check labelled `local-part-names-other-surname`. The
question class (`names-other`) is derived from that C2 check, so changing it
would move cases between classes and change every class's size and split.
That is a design/corpus-shape decision, left for a follow-up.
